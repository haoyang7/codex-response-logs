# 日志配置与排查

首次在 macOS 使用时，先完成下面的日志启用步骤，再启动查看器。[README 的快速开始](../README.md#快速开始) 提供完整上手顺序；本文补充日志来源、自定义路径与故障排查。

查看器读取已经存在的响应日志，并通过本地会话记录补齐名称、轮次和请求参数。它不会自动配置日志级别或重启 Codex。

## 让 macOS 桌面应用写出响应事件

已有完整日志时可以直接使用查看器。若日志中缺少响应事件，先结束进行中的任务并完全退出桌面应用，再通过应用标识启动：

```sh
open -b com.openai.codex \
  --env 'RUST_LOG=warn,codex_api=trace,tungstenite::protocol=trace,tungstenite::protocol::frame=off' \
  --env 'CODEX_MAX_LOG_LEVEL=debug'
```

`-b com.openai.codex` 使用应用标识查找已注册的桌面应用；应用文件名可能是 `Codex.app` 或 `ChatGPT.app`。如果系统找不到该标识，在访达中确认应用的实际位置，然后将 `-b com.openai.codex` 替换为 `-a "/实际路径/应用名称.app"`。

这些变量影响新启动的桌面应用。若旧进程仍在运行，打开应用通常不会重新加载环境变量。不同应用版本也可能改变日志路径、格式和级别传递方式，以实际写入磁盘的事件为准。

调试日志可能包含请求与对话内容，并增加磁盘占用。排查结束后按需恢复常规启动方式；查看器的响应保留上限不会清理 Codex 的原始日志。

## 数据来源

| 来源 | 用途 |
| --- | --- |
| `--log` 指定的文件 | 单文件解析，包括已有 `.log` 和原始 `data:` SSE 等格式 |
| 常规日志目录 | `--log-dir` 覆盖 `config.toml` 中的 `log_dir`；都未指定时使用 Codex home 下的 `log/` |
| macOS 桌面日志 | 默认 `~/Library/Logs/com.openai.codex`；可用 `--desktop-log-dir` 覆盖或 `--no-desktop` 禁用 |
| `state_5.sqlite`、`thread_history_1.sqlite` | 会话名称、会话文件路径和轮次；轮次查询需要 SQLite 3.25+ |
| 会话 JSONL | `turn_context` 的请求参数，以及 `token_usage_record.response_id` 的精确关联 |
| `logs_2.sqlite` | 可选启动诊断：是否存在名为 `codex_block_logs_insert` 的触发器；不验证其实际作用 |

常规日志目录可能为空。SSE / WebSocket 响应事件也可以位于 macOS 桌面日志中；页面的目录提示显示配置位置，记录中的传输类型取自实际事件。

目录解析顺序：

1. Codex home：`--home` → `CODEX_HOME` → `~/.codex`。
2. 数据库目录：`config.toml` 的 `sqlite_home` → `CODEX_SQLITE_HOME` → Codex home。
3. 常规日志目录：`--log-dir` → `config.toml` 的 `log_dir` → Codex home 下的 `log/`。

常规日志目录（`--log-dir` / `log_dir`）与数据库目录的相对路径按 Codex home 解析；`--log` 和 `--desktop-log-dir` 的相对路径按启动时的工作目录解析。路径中的 `~` 会展开。

`--home` 指向默认目录之外的位置时，不会自动混入默认桌面日志；需要时显式指定 `--desktop-log-dir`。`--log` 始终只读取指定日志文件，会话数据库仍用于关联。

```sh
# 使用另一个 Codex 配置目录
python3 codex_sse_watch.py --web --home /path/to/codex-home -n 200

# 指定常规日志目录，不扫描默认桌面日志
python3 codex_sse_watch.py --web --log-dir /path/to/logs --no-desktop -n 200
```

## 页面与记录问题

| 现象 | 检查方式 |
| --- | --- |
| 正在加载已有记录 | 查看页面中的阶段、文件数和已读取字节；首次加载会完整读取已有日志并关联会话，`-n` 仅限制展示条数。进度长时间不变时检查启动终端的错误及 `--status` 结果 |
| 无法连接查看器 | 页面会自动重连；确认启动终端仍在运行，并使用终端打印的地址。已加载的数据仍可查看，但此时无法确认后端采集状态 |
| 页面没有记录 | 展开「字段说明与采集状态」，确认日志路径、日志级别与文件更新情况；已有文件可用 `--log` 单独检查 |
| 只有响应，名称与请求参数为空 | 等待对应会话 JSONL 和数据库到达；确认数据库目录属于同一套 Codex 数据 |
| 首档或终档显示 `—` | 对应阶段没有可信字段；查看器不会由另一个阶段补齐，也不会按当前配置推断历史值 |
| `max → max` 但状态失败 | 两个阶段都记录了 `max`；详情中的错误和响应状态决定请求结果 |
| 耗时或 HTTP 状态为空 | 当前日志没有可靠来源；响应创建到完成的差值也不是完整客户端耗时 |
| 较早记录从表格移出 | 页面只展示最近 `-n` 条，后端最多保留 5000 条；原始文件仍由 Codex 管理 |
| 启动时未能检查 SQLite 日志 | 可选 `logs_2.sqlite` 被锁定、损坏或不可读；响应仍从文件采集，触发器诊断结果未知 |
| 启动检查发现 SQLite 触发器 | 只代表启动时存在同名触发器；是否影响写入取决于其定义。查看器从文件采集响应，修改数据库后需重启查看器以重新检查 |

查看器只接受明确来源的日志记录，不把普通日志正文中的 JSON 或 SSE 文本当作独立响应。损坏记录缺少可靠分隔时可能被跳过。只有通过响应 ID 关联的本地请求参数参与比较，不按时间相近猜测。

## 启动与停止问题

| 现象 | 处理方式 |
| --- | --- |
| 提示 `Codex.app` 不存在、错误代码 `260` | 固定应用路径与实际安装位置不符；使用上面的 `open -b com.openai.codex` 命令。若仍无法定位，在访达中确认应用位置，用 `open -a` 指定完整路径 |
| Python 版本过低或缺少 `tomllib` | 使用 Python 3.11+，并确认终端与双击脚本的 `python3` 指向同一版本 |
| 端口被占用 | 使用 `--port 0` 获取空闲端口；服务不会把任意占用端口的程序当作本实例 |
| 重复启动没有应用新的参数 | 同目录同端口会复用已有实例；停止后用新参数重新启动 |
| 浏览器无法连接 | 查看启动终端是否仍在运行，使用打印出的 `http://127.0.0.1:端口/` 地址 |
| 直接打开 HTML 无法读取数据 | 通过 `--web` 启动服务，再使用本机 HTTP 地址 |
| 关闭网页后采集仍在运行 | 在启动终端按 Ctrl+C，或从同目录执行 `--stop --port 实际端口` |
| 移动目录后无法控制原实例 | 控制凭据和脚本身份属于启动目录；从原目录执行停止，或在原终端按 Ctrl+C |

状态和停止操作使用 `.runtime/` 中的临时令牌。自动分配端口时，需要将启动时打印的实际端口传给 `--status` / `--stop`。`--no-open` 只关闭自动打开浏览器，不会把程序变为后台守护进程。
